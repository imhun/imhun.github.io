原文：Cyclic trait solving，Niko Matsakis，2026-08-10 系列：Cyclic Trait Impls

Niko 开了个系列聊 Rust 能不能允许循环的 trait 实现。这问题他惦记了好几年，最近才觉得摸到门路。第一篇不讲方案，先把问题交代清楚：现在为什么不让循环，后来为什么又需要。

现在的规矩：实现必须是归纳的

目前 Rust 要求 trait 实现是“非循环”的，也就是归纳式（inductive）。拿 Dump 举例：

3

trait Dump {
    fn dump(&self);
}

给 i32 和几个容器类型各写一个实现：

// Impl I
impl Dump for i32 {
    fn dump(&self) {
        println!("{self}");
    }
}

// Impl RC
impl<T> Dump for Rc<T>
where
    T: Dump,
{
    fn dump(&self) {
        T::dump(self)
    }
}

// Impl Opt
impl<T> Dump for Option<T>
where
    T: Dump,
{
    fn dump(&self) {
        if let Some(v) = self {
            T::dump(v)
        }
    }
}

再给递归类型 List 写一个：

struct List<T> {
    value: Rc<T>,
    next: Option<Rc<List<T>>>,
}

// Impl L
impl<T> Dump for List<T>
where
    T: Dump,
{
    fn dump(&self) {
        Dump::dump(&self.value);
        if let Some(n) = &self.next {
            Dump::dump(n);
        }
    }
}

现在要证 List<i32>: Dump，往下推是这样：

  • 用 Impl L：只要 i32: Dump 成立，List<i32>: Dump 就成立
    • 用 Impl I：i32: Dump 成立 ✓

每一步都依赖一个更小的前提，最后落在 i32: Dump 这种不用再证的事实上。全程没有拿 Impl L 去证明 Impl L 自己——这就是“归纳”的含义。

想要循环的理由：derive 生成了一堆多余约束

不能循环推理，听着本就该如此。逻辑论证里不许循环，不能说“Niko 喜欢 Rust，因为 Niko 喜欢 Rust”。

但有些场景你还真得这么用，典型的就是 derive。

上面 Dump 那个实现只有一条 where 子句 T: Dump。如果写个 derive 宏，#[derive(Dump)] 生成的基本就长这样。问题是这个结果往往不是你想要的，看 #[derive(Clone)]：

// Impl LC1
impl<T> Clone for List<T>
where
    T: Clone, // <-- 生成了，但其实不必要
{
    fn clone(&self) -> Self {
        List {
            value: Clone::clone(&self.value),
            next: Clone::clone(&self.next),
        }
    }
}

这个 impl 要求 T: Clone，可 List 的字段只用到 Rc<T>，所以 T 不会 clone 也无所谓。编译器要判断这一点，得去分析字段——某种意义上它确实能做到，这正是循环 trait 求解要解决的问题。

但 derive 宏做不到：它看不到别的类型的定义，要判断 T: Clone 是否必要，得先知道 Option 和 Rc 长什么样。

换个 impl 写法就能表达这个意思——不按类型参数加约束，改按字段类型加：

1
2
3
4
5
6
7
8

// Impl LC2
impl<T> Clone for List<T>
where
    Rc<T>: Clone,
    Option<Rc<List<T>>>: Clone,
{
    // .. 同上 ..
}

这样就精确了：只需要 Rc<_> 和 Option<Rc<_>> 能克隆，两个都不要求 T: Clone。这个思路叫 perfect derive，是个想了很久的目标。

Clone 能过，Dump 过不去

Clone 这个例子甚至用不上真正的循环推理：

  • 证 List<i32>: Clone
    • Rc<i32>: Clone —— impl<T> Clone for Rc<T> 没有 where 子句（默认的 Sized 先忽略）
    • Option<Rc<List<i32>>>: Clone 走 impl<T> Clone for Option<T> where T: Clone，需要
      • Rc<List<i32>>: Clone —— 同样不需要什么前提

同一套写法搬到 Dump 上就绕住了：

// impl L1
impl<T> Dump for List<T>
where
    Rc<T>: Dump,                    // 原来是 T: Dump
    Option<Rc<List<T>>>: Dump,      // 新增的（原文这里漏了 ": Dump"）
{
    fn dump(&self) {...}
}

证 List<i32>: Dump 要满足两条 where 子句：

  • Rc<i32>: Dump —— Rc 的 impl 要求 i32: Dump，成立
  • Option<Rc<List<i32>>>: Dump —— 这里绕回去了。Option 的 impl 要求证 Rc<List<i32>>: Dump，Rc 的 impl 又要求证 List<i32>: Dump，而这就是最开始要证的东西

出现了循环。

循环不能全收：supertrait 就是反例

那循环全接受行不行？就上面这几个例子来说，确实看不出问题。但只要考虑 supertrait，就不行了：

1
2
3
4
5
6
7

trait Magic: Copy { }

// Impl M
impl<T> Magic for T
where
    T: Magic,
{}

一旦无脑接受循环，这组实现就能“证明”任何类型都是 Copy，哪怕它根本没有 Copy 的实现：

  • 要证 String: Copy。既然实现了 Magic 的类型必然实现 Copy，那
    • 先证 String: Magic。用 Impl M，要求证明 String: Magic——循环，接受它

于是 String: Copy 就被“证”出来了。可 String 根本没有 Copy 实现。这段推理显然是错的。

错在哪其实看得出来：Impl M 没有提供任何信息。它就是一句同义反复，T: Magic 成立当且仅当 T: Magic 成立。这句本身没错，但“给 Magic 写实现”本该同时说明 supertrait Copy 也实现了——这里并没有。

那么问题变成：为什么该拒绝 Impl M，却接受 Dump 的 impl L1？两者最后都得到循环证明，差别在哪。这正是后面几篇要解决的事情。

什么叫 trait 系统 sound

顺着上面那个问题往下走，会碰到一个更基础的问题：trait 系统 sound（健全）到底是什么意思。听着像废话，但 Niko 说他想了很久才想清楚。

有两种让人满意的定义。一种是把 trait 转成 dictionary-passing style，Nadri 在那篇博客里讲了，值得一读。这里给另一种，不需要转成依赖类型程序。

粗略地说：只要 trait 系统接受了程序 P，P 里就不可能存在某个函数，它“相信”某 Trait 对 T 成立，实际上却没有可用的 impl。

按这个定义，Magic / Copy 那组实现很容易写出反例：

trait Magic: Copy {}

impl<T: Magic> Magic for T {}

fn is_copy<T: Copy>() {
    // 这个函数相信 `T: Copy`
}

fn main() {
    // 这里能通过，是因为我们认为
    // * `String: Magic` 成立，因为
    //     * `String: Magic` 成立，而循环被接受了
    // 而 `String: Magic` 蕴涵 `String: Copy`
    is_copy::<String>();
}

任何 sound 的类型系统都得拒绝这段程序：它一旦跑起来就会走到 is_copy::<String>，而根本不存在适用于 String 的 Copy impl。

后面几篇

这篇主要是铺场子：把要解决的问题说清楚，也就是允许好的循环实现、禁止坏的。坏的这里只举了一个，实际上花样很多，有些是编译器现在就处理错的，有些要等开始允许循环之后才会错。

动机也算复杂：他想要 perfect derive，同时这也是 trait 语义里一直悬着的问题，想在推进别的任务之前定下来。auto trait（比如 Send）和其他 trait 的行为不一致，本身就是个别扭的地方；对底层逻辑理解不够，做扩展时很容易出错。

后面几篇会讲得更深：走过的死路以及为什么走不通、正在考虑的方案，还会涉及 coinduction 和 productivity、模态逻辑和 later modality，最后看看这些技术能不能顺手解决 specialization。
