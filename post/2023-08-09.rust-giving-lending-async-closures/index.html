giving 与 lending，以及 async 闭包

2023-08-09
技术
约 1022 字 预计阅读 3 分钟 次阅读

文章目录

来源：Giving, lending, and async closures，Niko Matsakis，2023-05-09

同步闭包和异步闭包的区别，本质上是 giving trait 和 lending trait 的区别：

返回值例子
giving与 self 无关，拿到的是所有权Iterator 的 next 返回 Option<Self::Item>
lending从 self 借来AsMut::as_mut 返回 &mut T；lending 迭代器返回指向自己内部缓冲区的引用

这个区别决定了泛型代码能做什么。giving 的迭代器可以连取两个 item 都留着用：

1
2
3
4
5

fn take_two_v1<T: Iterator>(t: &mut T) -> Option<(T::Item, T::Item)> {
    let i = t.next()?;
    let j = t.next()?; // i 仍然有效
    Some((i, j))
}

换成 lending 版本就编不过——第一个值在取第二个时已经被覆盖了。作为交换，迭代器可以用内部缓冲区。这不是 Rust 强加的限制：Java 里那个复用 ByteBuffer 的迭代器就是 lending 的，只是语言表达不出来，所以写两次 next 会静默拿到同一个值。Rust 的区分表达的是固有复杂度。

每个 giving trait 都是 lending trait 的子集，相当于“恰好不借出的 lending”。反过来可以把这个事实写进约束，让 lending 迭代器也能用 take_two：

1
2
3
4
5
6
7
8
9

fn take_two_v3<T, U>(t: &mut T) -> Option<(U, U)>
where
    T: for<'a> LendingIterator<Item<'a> = U>,
    // 不管 'a 是什么，Item 永远是 U；而 U 不可能引用 'a
{
    let i = t.next()?;
    let j = t.next()?;
    Some((i, j))
}

Item<'a> = U 相当于断言“这个迭代器产生的值永远不从 self 借”。当然也就用不了真正需要借出的那些迭代器。

为什么 Iterator 不能就地改，FnMut 却能

两者都是 giving trait，都要变成 lending 才有 async/借出版本。但能不能就地改，结论相反。

Iterator 不能。 因为以 T: Iterator 为泛型参数的函数（比如 take_two_v1）依赖它是 giving 的。如果 Iterator 变成 lending，这些函数就编不过；那就必须区分“任意 giving 迭代器”和“任意 lending 迭代器”——既然是两件事，干脆做成两个 trait。

FnMut 能。 原因是闭包强制使用特殊语法：写 F: FnMut(u32) 实际是 F: FnMut<(u32,), Output = ()>，永远带着 Output 的值。所以今天写不出“以 FnMut 为泛型参数、又不指定 Output”的函数，也就没有代码依赖旧的 giving 语义。

改法是把关联类型加上生命周期参数，并把脱糖规则改成：

1
2

// F: FnMut() -> R  变成
for<'a> F: FnMut<(), Output<'a> = R>

还要让 F::Output 在不指定生命周期参数时也合法。

剩下没解决的问题

光把 Fn* 改成 lending 还不够。要支持

1

fn take_closure(x: impl FnMut() -> impl Future<Output = bool>) {}

还得决定这里的 impl Trait 怎么解释。想要它变成对 Output 的约束：

1
2
3

where
    F: FnMut<()>,
    for<'a> <F as FnMut<()>>::Output<'a>: Future<Output = bool>,

这样 Output 就允许捕获 'a，调用闭包后必须 await 完才能再调——正是想要的效果。麻烦在于这跟现有解释不一致：impl Iterator<Item = impl Debug> 今天是脱糖成两个新参数 <F, G> 的，而且 impl Iterator<Item = (impl Debug, impl Debug)> 这种写法根本表达不成 bound（RFC #2289 提出用 Item: Debug 的新语法解决）。顺着这条路走会有一堆地方要理清，作者担心最后做出一个细微变体太多、对用户很困惑的东西。
