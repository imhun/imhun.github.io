来源：Tree Borrows，Neven Villani、Johannes Hostert、Derek Dreyer、Ralf Jung，PLDI 2025（杰出论文） PDF ｜ Artifact

Stacked Borrows 的继任者。把“引用的别名关系”从栈换成树，解决三个问题：拒绝读-读重排、引用的访问范围写死、two-phase borrows 处理得草率。实测在 3 万个 crate 上比 Stacked Borrows 少拒 54% 的测试用例。

为什么需要别名模型

Rust 的类型系统给编译器提供了很强的别名信息：引用要么是别名要么是可变的，不会同时是两者。编译器想拿它做进程内优化：

1
2
3
4
5

fn write_both(x: &mut i32, y: &mut i32) -> i32 {
    *x = 13;
    *y = 20;
    *x // 变换：直接返回 13
}

两个 &mut 按类型系统不可能别名，所以函数必然返回 13，最后一次读 *x 可以换成常量。

但 unsafe 能绕开这个前提：

1
2
3
4
5
6

fn main() {
    let mut x = 42;
    let ptr = &mut x as *mut i32;
    let val = unsafe { write_both(&mut *ptr, &mut *ptr) };
    println!("{val}");
}

不开优化打印 20，开了打印 13——优化改变了行为。所以这段必须是未定义行为（UB）。

任务因此变成：定义 UB，使得这类代码被拒绝、所有 safe 代码被接受，而且合理写法的 unsafe 代码也能通过。最后一条同样重要——如果正确写 unsafe 要费很大劲，这门语言就没人用了。

Stacked Borrows 的三个问题

Stacked Borrows 用栈记录当前有效的指针（x 在栈底，ref1 在上，ref2 在最上），要求所有使用严格嵌套：ref1 一被使用，ref2 就失效。

问题一：禁止读-读重排。

1
2
3
4
5

let mut x = 42;
let ref1 = &mut x;
let ref2 = &mut *ref1;
*ref2 = 12;
println!("{ref1}"); // 打印 12

ref2 是从 ref1 重借用来的，这里读 ref2 再读 ref1 没问题（嵌套顺序）。但把两次读调换顺序就成了 UB——重排相邻的读是基本优化，这个代价不小。

问题二：引用的访问范围是静态的。

引用创建时，类型就决定了它能访问的内存范围，范围之外永远碰不到。从 C 过来的人习惯取数组首元素的引用、转成裸指针、然后访问整个数组——这种写法会被拒。模型和程序员预期的这种错位，在真实代码里制造了大量 UB 报告。

问题三：two-phase borrows 处理得草率。

Rust 的 two-phase borrows 让某些可变引用先进入“预约阶段”（允许只读别名），直到第一次写才要求唯一。Stacked Borrows 当初不支持这个特性，后来在实现里把这类引用当裸指针处理，结果出现很反直觉的行为：

1
2
3
4
5

fn write(x: &mut i32) { *x = 10; }
let x = &mut 0;
let y = x as *mut i32; // 从 x 派生裸指针
write(x);              // 写 x
unsafe { *y = 15 };    // 用裸指针写

这段被接受，但把 write(x) 内联展开后反而不被接受。原因是 write(x) 隐式展开成 write(&twophase x)，而 &twophase 被当成了裸指针。行为随内联与否变化，既让人困惑，也削弱了优化空间。

核心：树

1
2
3
4

let mut root = 42;
let ref1 = &mut root;
let ref2 = &mut *ref1;
let ref3 = &mut root;

1
2
3
4

root
├── ref1
│   └── ref2
└── ref3

规则很简单：每个新引用作为“创建它的那个节点”的子节点插入。树比栈自然，因为每个引用只有唯一的父节点（它是从哪个变量/引用创建的），而栈额外强加了“同一时刻最多只有一个子节点有意义”——这正是 two-phase borrows 不成立的地方：预约阶段里可以有多个共享引用作为兄弟和平共存，等可变引用激活时再一起失效。

由此，引用不只是内存地址，而是（地址, tag）对，tag 决定它在树上的节点。

每次内存访问会“通知”树上所有节点，每个节点跑一个状态机，决定这次访问是被允许（可能切到别的状态）还是 UB。状态机的输入字母表是四种：

1
2

↓R  local read     ↓W  local write
↑R  foreign read   ↑W  foreign write

local 指访问用的 tag 是这个节点自己或它的后代；foreign 指访问来自父节点或堂兄弟。

状态机怎么一步步搭出来

最朴素版：Unique / Disabled

1
2
3
4

let mut root = 42;
let x = &mut root;
*x += 1;
root = 0

x 是 root 的子节点。借用检查器会判定 x 的生命周期从 &mut root 开始、到 root = 0 结束——那里父引用收回所有权，x 必须死。对应到状态机只需要两个状态：Unique（活着）和 Disabled（死了）。Unique 容忍任意本地访问；一旦遭遇外来访问，说明父引用收回了所有权，切到 Disabled，之后再本地访问就是 UB。

拿这个朴素模型检查开头的反例：

1
2
3
4
5
6

let mut root = 42;
let ptr = &mut root as *mut i32;
let (x, y) = unsafe { (&mut *ptr, &mut *ptr) };
*x = 13;
*y = 20;
let val = *x;

x 和 y 是堂兄弟。*x = 13 对 x 是本地写、对 y 是外来写 → y 变 Disabled；接着 *y = 20 对 Disabled 节点做本地写 → UB。符合预期。

加 Reserved：支持 two-phase borrows

标准例子是 v.push(v.len())，脱糖后大致是：

1
2
3
4

let v_for_push = &twophase v;
let v_for_len = &v;
let len = Vec::len(v_for_len);
Vec::push(v_for_push, len);

朴素模型下，Vec::len 的读对 v_for_push 是外来读 → 直接 Disabled → 后面 push 就成了 UB。但这明明是合法代码。

Rust 编译器的解法（two-phase borrows）是让可变引用先经历预约阶段：这期间允许任意读访问，哪怕是别人在读；第一次写（激活）之后才变成完整的可变引用。

模型里对应新增 Reserved 状态，作为可变引用的起始状态：Reserved 允许本地和外来读；遭遇本地写（激活）→ Unique；Unique 再遇外来访问 → Disabled。

注意一个简化：源码里所有可变引用都以 Reserved 开始，不区分编译器是否真的做了 two-phase 处理。这样把隐式引用写成显式时行为不会变。

加 Frozen：支持读-读重排

在别名模型里，读不是无副作用的——读会推动状态机。上面 Unique 遇外来读直接变 Disabled，导致下面两种写法不等价：

1
2

let vx = *x; let vy = *y;
let vy = *y; let vx = *x;

以 x 是 root 的子节点且处于 Unique 为例（let mut root = 0; let x = &mut root; *x = 42;），先读 x 再读 root 没问题，反过来先读 root（对 x 是外来读）就把 x 打成 Disabled，后面再读 x 就 UB。

问题出在“外来读让一个还能读的引用丢掉读权限”。修法是插入一个中间状态 Frozen：Unique 遇外来读 → Frozen（仍可读，不可写），Frozen 遇外来写 → Disabled。

于是两种读序最终都落到同一个状态。这是少见的情形——减少 UB 反而多出一种优化。

一个引用覆盖多个地址

内存按 allocation 划分，地址是 (allocation, offset)。每个 allocation 有一棵 tag 树，而且每个 offset 各有自己的状态机实例——同一个人 tag 在不同偏移可以是不同状态。

一次访问跨多个地址（比如 4 字节的读）时，逐个更新这些地址上的状态机；只要有任何一个进入 UB，整个访问就是 UB。

共享引用和裸指针：不需要新权限

共享引用恰好就是 Frozen：允许本地和外来读、本地写触发 UB、外来写变 Disabled。所以共享引用直接以 Frozen 起始。这也给了“Unique → Frozen”一个新的解释——可变引用守不住唯一性时，被降级成共享引用。

裸指针在 Tree Borrows 里创建是空操作：不生成新 tag，直接继承父引用的 tag。

1
2
3
4
5
6
7
8

let mut root = 42;
let ref1 = &mut root;
let ptr1 = ref1 as *mut i32;
unsafe {
    *ref1 = 43;
    *ptr1 = 44;
    *ref1 = 45;
}

模型眼里 ref1 和 ptr1 是同一个 tag，三次交错赋值完全没问题。父引用失效时，从它派生的所有裸指针一起失效。

动态访问范围

1
2
3
4

let mut v = [0u8, 0];
let x = &mut v[0];
let y = (x as *mut i32).add(1);
unsafe { *y = 1; }

x 的类型只覆盖第一个元素，而 y 指向第二个元素——越出了 x 的类型范围。这种写法在底层代码里不罕见（比如数据块前缀描述后面数据的形状，这种信息静态类型表达不了）。

Tree Borrows 接受它：&mut v[0] 会在整个 allocation 上为新引用建立状态机，不只是类型指示的那一段。类型范围外的位置一开始标记为“未使用”，用到了才参与判定，于是引用范围可以动态扩大。同时模型仍然保证：从不同可变引用派生的裸指针只能改互不相交的内存。

内部可变性

UnsafeCell<T> 标记的类型不遵守常规别名保证。它们的共享引用基本等同于裸指针，因此继承父引用的 tag。

可变引用在激活之后和普通可变引用没区别，但预约阶段要容忍外来写——因为共享引用此时可以写：

1
2
3
4
5
6

fn foo(c: &mut Cell<i32>, n: i32) { *c.get_mut() = n; }
let mut c = Cell::new(1);
let c_mut = &twophase c;
let c_shr = &c;
let val = Cell::replace(c_shr, 42); // 这是一次写
foo(c_mut, val);

Cell::replace 的写对 c_mut 是外来写，不能被当成违约。所以加一个 ReservedIM 状态（IM = interior mutable）：和 Reserved 一样，但允许外来写，作为内部可变类型的可变引用的入口状态。

protectors：让传进函数的引用活到函数结束

到这里模型能接受所有 safe 代码，但证明不了编译器已经在做的优化。编译器假设：作为参数传入的引用，在整个函数调用期间保持唯一/不可变。

1
2
3
4
5

fn write_and_call(x: &mut i32, opaque: impl Fn()) {
    *x = 13; // 变换：删掉这次写
    opaque();
    *x = 20;
}

想删掉第一次写，但 opaque 是任意未知代码。直觉上 opaque 不可能碰到 x 指向的内存——它没有 x 的别名，一旦访问就是 UB。

问题在于 opaque 可以永不返回：

1
2
3
4
5
6
7
8

let mut root = 42;
let ptr1 = &mut root as *mut i32;
let opaque = move || {
    let ptr2 = ptr1;
    println!("{}", unsafe { *ptr2 });
    std::process::exit(0); // 直接退出
};
write_and_call(unsafe { &mut *ptr1 }, opaque);

opaque 用外来 tag 读了 root（x 变 Frozen），然后退出。按前面的模型这不构成 UB（x 不再被使用），但优化会改变输出。所以需要 protectors。

做法：给每个 tag 挂一个布尔标记。函数调用开始时，为所有参数引用生成新 tag（相当于重新借用）并标记为 protected，函数返回时解除。被保护的 tag 不允许变成 Disabled——本该变 Disabled 的操作直接判 UB。

还有一个更细的补充。要证明下面这个“把写提前”的优化，得保证函数里只要写过 y，期间就不能出现过外来读（无论先后）：

1
2
3
4
5

fn read_write(x: *const i32, y: &mut i32) -> i32 {
    let val = unsafe { *x };
    *y = 20; // 变换：把这次写提前
    val
}

于是 Reserved 上加一个 conflicted 标记：发生过外来读的 Reserved 不能再变成 Unique，本地写直接 UB。

合起来是一句好记的规则：任何作为参数传入函数的可变引用，只要同时遇到外来读和本地写，无论顺序如何都是 UB。

retag 隐含执行一次读

protector 保证参数在函数期间活着，于是可以支持“插入多余的读”：

1
2
3
4
5
6

fn repeat(x: &i32, n: usize, opaque: impl Fn(i32)) {
    // let val = *x;      变换：插入一次读
    for _ in 0..n {
        opaque(*x);        // 变换：把 *x 换成 val
    }
}

n 为 0 时，插入的读在原程序里根本不存在，有可能触发 UB。所以模型规定：每次生成新 tag（retag——创建引用时、每次函数调用开始时）都隐含执行一次读，读的大小由引用的类型决定。注意只隐含读，不隐含写，&mut 也一样。

protector 结束时也要做隐含访问：用过的 Reserved / Frozen 位置隐含一次读，用过的 Unique 位置隐含一次写，都只作用于外来 tag。一进一出各做一次，模型才有最大自由度去重排和插入访问——这也正是下面那个“合并两次写”的优化能证明过关的原因（去掉这个隐含访问就有反例）：

1
2
3
4
5
6

fn write_opt(x: &mut i32, f: impl FnOnce(), g: impl FnOnce()) {
    f();
    *x = 10;   // 变换：改成写 0
    g();
    *x = 0;    // 变换：删掉
}

实验：Miri + 3 万个 crate

作者把 Tree Borrows 实现在 Miri 里，并把别名模型做成可配置的（需要适度重构 Miri 内部）。然后跑 crates.io 下载量最高的 3 万个 crate 的测试套件：

  1. 过滤轮：两个模型都关，剔除 Miri 不支持、本身就失败、超时（60 秒）、以及与别名无关的 UB
  2. 比较轮：剩下的测试分别开 Tree Borrows 和 Stacked Borrows 各跑一遍（超时放宽到 150 秒）

总测试数 674 748，过滤后约 68.2% 通过。

Stacked BorrowsTree Borrows
因别名违规失败6 5683 023
单独通过—少 53.97%
只有自己通过、对方不通过31—

也就是说，Stacked Borrows 拒掉的代码里超过一半被 Tree Borrows 接受了；而 Tree Borrows 新拒掉的只有 31 个测试，来自 12 个 crate。逐一看过：

  • moka、mini-moka、mshv-bindings、soa-derive 各 1 个，原因都是依赖 Stacked Borrows 的那个“quirk”，作者都提交了补丁且被接受
  • deno_core 12 个，原因是有个 struct 本该标成内部可变类型，而 Stacked Borrows 因为 quirk 加上草率的 two-phase 处理没报出来；修了约 30 行，是这批里最复杂的
  • bitvec 1 个，社区已有补丁但未合并，crate 似乎已被放弃
  • spinning 1 个，竞争条件导致的 flaky test，Stacked Borrows 下也会出现
  • nostd_async 6 个，作者自己判定“根本不可靠”后删库

两个要留意的点：一是 Tree Borrows 下的超时比 Stacked Borrows 多一个数量级，说明 Miri 的性能还需要继续优化；二是这组数字其实对 Tree Borrows 不利——Rust 生态这些年已经被引导着写 Stacked Borrows 兼容的代码了。

形式化证明

用 Rocq（原 Coq）形式化模型，在 Simuliris（建立在 Iris 上的关系分离逻辑框架，专门处理并发程序优化的上下文精化，自带对未知代码的推理规则）之上搭了一个 “Tree Borrows Optimizations Program Logic”，整个证明约 32 000 行。

它证明的能力：对 protected 引用，可以任意插入、删除、重排读写，只受三条限制：

  1. 被变换的 &mut 不能被中间的未知代码使用
  2. 激活写（Reserved → Unique 那一次）不能挪动，新的写只能插在它之后
  3. protector 结束后，或者这个 &mut 交给未知代码后，值必须重新对上，之后不再允许插入/删除/重排

对照 Stacked Borrows：几乎所有的优化都保住了，唯一的例外是“在原程序第一次写之前插入新的写”这类。这是为了兼容真实代码付出的代价。

Tree Borrows 还新证明了读-读重排是 sound——Stacked Borrows 证明不了这个。

没有 protector 的引用优化空间小得多：生命周期在最后一次使用时结束，所以“把最后一次使用往后挪”一般不允许。而且这些变换只在 Rust 里成立是因为数据竞争本身是 UB，而这篇论文用的是简单的顺序一致语义，也就是允许有竞争行为。

和 Stacked Borrows 的对照

Stacked BorrowsTree Borrows
结构栈（等价于分叉数为 1 的树）树
可变引用起始态UniqueReserved（所有 &mut 都当 two-phase）
权限何时确定创建时定死，直到失效每个节点一个状态机，随访问变化
Unique 遇外来读直接 Disabled变 Frozen，仍可读
two-phase borrows当裸指针处理真正的预约阶段
裸指针的 tag独立的 tag（SharedRW）继承父引用的 tag
访问范围静态，由类型决定动态，按实际使用
参数保护有，但更简单（无隐含访问、无 conflicted）有，含隐含访问与 conflicted 标记

两个模型在“谁接受更多代码”上其实不可比。Tree Borrows 更严的少数情形长这样：

1
2
3
4
5
6

let mut root = 0;
let tmp = &mut root;
let ptr = tmp as *mut i32;
unsafe { *ptr = 1; }
let _val = root;
unsafe { *ptr = 2; }

Stacked Borrows 接受：ptr 是 root 的“孙子”，读 root 只让 tmp 失效，ptr 还是 SharedRW，所以还能写。Tree Borrows 拒绝：ptr 继承了 tmp 的 tag，写完 1 之后是 Unique，读 root 把它打成 Frozen，再写 2 就是 UB。

Stacked Borrows 之所以有这种“quirk”，是为了接受某个常见的 unsafe 写法，但那段动机代码里并没有这两次夹着读的写。作者的判断是：上面这种交错写法大概只是碰巧被 Stacked Borrows 接受了。

边界

Tree Borrows 不是借用检查器，也不建议改借用检查器。借用检查器属于类型系统，Tree Borrows 属于操作语义——它定义的是“unsafe 代码什么时候算 UB”，从而给编译器的别名优化划出地盘。两者有关系但不是一回事：类型安全的推论是“类型正确的 safe 程序绝不产生 UB”，这一条在 Miri 上大量测过，但还没形式化证明。

  • 证明框架目前有两个大限制：(a) 可变引用的激活写不能往下重排；(b) 需要推理数据竞争的优化还不能验证。要把数据竞争和树形别名模型放在一起推理相当复杂，可能得重新设计验证框架
  • 现在有办法测程序是否符合 Tree Borrows（Miri），也有办法验证依赖 Tree Borrows 的优化（Rocq + Simuliris），但还没有框架能证明一个程序在 Tree Borrows 下行为正确——Louwrink 对 Stacked Borrows 做过这件事
