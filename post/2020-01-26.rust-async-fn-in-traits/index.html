trait 里的 async fn 为什么难

2020-01-26
技术
1100 words 3 mins read times read

Contents

    • 关联类型这一步躲不掉
    • Send 约束是纯语法灾难

    • 相关

来源：Async fn in traits are hard，Niko Matsakis，2019-10-26

今天想在 trait 里写 async fn，答案是用 async-trait。它把

1
2
3
4

#[async_trait]
trait Database {
    async fn get_user(&self) -> User;
}

脱糖成

1
2
3

trait Database {
    fn get_user(&self) -> Pin<Box<dyn Future<Output = User> + Send + '_>>;
}

注意返回的是 dyn Future，而不是编译器为普通 async fn 生成的 impl Future。为什么在 trait 里就非得装箱，就是这个题目的全部难点。

三个麻烦

麻烦说明
trait 里不能写 -> impl Trait逻辑上它等价于关联类型，但 async fn 会捕获全部参数，那个关联类型必须带生命周期参数——也就是 GAT
Send 约束写不出来想表达“返回的 future 是 Send”，得写 for<'s> D::GetUser<'s>: Send；async fn 自带泛型时更夸张
dyn Trait 装不下dyn 必须指定所有关联类型，而每个 impl 的 future 类型都不同，指定了就没有多态的意义

关联类型这一步躲不掉

把 async fn get_user(&self) -> User 一层层剥开：

1
2
3
4
5

// 第一步
fn get_user(&self) -> impl Future<Output = User> + '_;
// 第二步
type GetUser<'s>: Future<Output = User> + 's;
fn get_user(&self) -> Self::GetUser<'_>;

's 必须有，因为 async fn 捕获了 &self。所以 trait 里的 async fn 直接依赖 GAT。GAT 概念上不复杂，难的是 rustc 里还没实现——可能得先把 rustc 迁到 chalk。

Send 约束是纯语法灾难

实际写起来长这样：

1
2
3
4
5
6

fn finagle_database<D: Database>(d: &D)
where
    for<'s> D::GetUser<'s>: Send,
{
    spawn(d.get_user());
}

四个问题叠在一起：

  • GetUser 是手工脱糖时编出来的名字，用户实际该写什么？
  • for<'s> 本身就难写
  • 一个 trait 有几个 async fn，就得列几条
  • 一旦写进签名，“哪些 future 必须 Send”就成了对外承诺，改动会破坏调用方——semver 隐患

async fn 自己带泛型参数时更难看：

1
2
3
4
5

trait Foo {
    async fn bar<A, B>(a: A, b: B);
}
// 需要的约束是
for<A: Send, B: Send> { S::bar<A, B>: Send }

方向大概是要有个 async Send 之类的约束，展开成对 D 以及它可能返回的所有 future 的 Send 要求。同样的问题在返回位置用 impl Trait 时也存在，所以语法最好做得更通用、不绑定 async。

dyn 这条路要预先做两个决定

想要 dyn Database，就想让 GetUser 不被指定，能想到的默认值是 Box<dyn Future>（更顺手的话 Pin<Box<dyn Future>>）。但：

  • 用 Box 有点随意，Rust 别处不这么特殊对待 Box
  • 真实的 impl 并没有装箱，它内联返回一个 future 类型，所以还要一个自动生成的 shim 去调函数、装箱、返回
  • dyn Future 把底层类型藏了（这正是它的用途），于是 auto trait 也失效——还得额外指定这个 future 是不是 Send

async-trait 就是绕开这三件事的产物

它做了什么绕开了什么
返回 dyn Future 而不是 impl Future关联类型 / GAT，以及 Send 约束的书写
替你选 Pin<Box<dyn Future + Send>>dyn 必须预先决定的指针形式和 Send 属性

代价只有一次装箱。而且只对跨 trait 边界的 async fn 装箱，和“所有 future 都装箱”是两回事——多数语言是后者，所以这点开销基本可以忽略。

唯一没解决的是命名：关联类型叫什么，用户怎么写。有过 typeof 表达式之类的提案。
