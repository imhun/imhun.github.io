Intel Mac 上的 Homebrew 退休计划：工具链搬去 conda-forge

2019 款 MacBook Pro 16，i9-9880H，x86_64，macOS 26.7.3。这台机器上 Homebrew 已经很难用了：一次 brew upgrade 13 个包跑了 7656 秒，两个多小时，风扇全程起飞。

查了一下，brew info --json=v2 jq 里 bottle.stable.files 只剩 sonoma 一个 tag。macOS 26 拿不到匹配的 Intel bottle，于是每个包都在本机源码编译。CPU 是 8 核，编译 Rust 写的 CLI 一个就要十几分钟。

conda-forge 的 osx-64 通道一直有预编译包，解包即用。于是一个下午把 CLI 全搬了过去，最后 brew 剩 0 formula、0 tap、3 个 cask。

结果先放这

项目迁移前迁移后
brew formula690
brew tap若干0
brew cask123
conda 前缀02
磁盘—删旧前缀省 2.5G，Caskroom 449M → 36K

现在这台机器上，CLI 由 micromamba 管，GUI 应用由 brew cask 管，两个系统互不干扰。

哪些东西搬得动、哪些搬不动，先说清楚：

  • 能搬：命令行工具、语言运行时、构建工具、系统库
  • 搬不动：macOS GUI 应用（conda-forge 基本不收）
  • 搬不动：linux-only 的包，比如 proxychains-ng
  • 别搬：被大量包当 :build 依赖的 cmake，删了反而每次编译都要重新装

装 micromamba，配国内源

不装完整的 conda，用 micromamba，单文件二进制，没有 base 环境的 Python 负担。

1
2
3

mkdir -p ~/.local/bin
curl -Ls https://micro.mamba.pm/api/micromamba/osx-64/latest \
  | tar -xvj -C ~/.local bin/micromamba

然后写 ~/.mambarc：

1
2
3

channels:
  - https://mirrors.tuna.tsinghua.edu.cn/anaconda/cloud/conda-forge
  - nodefaults

nodefaults 这一行不能省。不写的话 Anaconda 官方的 default 通道会掺进来，同一个包两个来源版本混在一起，求解器偶尔会给出莫名其妙的降级方案。

国内源用清华 TUNA，中科大 USTC 也行。micromamba 会先尝试 shard 索引，镜像没有时自动回退到 flat repodata，多几秒，不影响结果。

前缀到底要分几个

一开始我按用途拆了 6 个前缀：cli2、gitonly、gpgwget、clitools、jvm、go。好处是装的时候互不干扰，坏处是一周后就记不清哪个工具在哪个前缀里，PATH 里得挂 6 条。

后来合并成两个：

1
2

~/opt/main    93 个包   coreutils / git / go / zig / jdtls / maven / jq / xz / yarn ...
~/opt/gnupg   24 个包   gnupg / pinentry / dos2unix

gnupg 单独放不是洁癖，是依赖真的打架：

1
2

git 2.56.1        需要  libintl >= 1.0
libgpg-error 1.61 需要  libintl <  1.0

pinentry 和 dos2unix 跟 gnupg 同一条链，一起隔离。

真想全并成一个也能解出来，代价是 git 从 2.56.1 降到 2.56.0、libintl 从 1.0 降到 0.25.1。为一个补丁版本降级核心库不划算，两个前缀就两个前缀。

合并本身不难，顺序重要：

  1. 建新前缀，把包一次装齐
  2. 逐包核对文件在不在
  3. 重建 /usr/local/bin 里的软链
  4. 全量跑一遍 --version
  5. 最后才删旧前缀

第 5 步别提前。我见过有人在验证之前就把旧目录删了，结果 gpg 的 pinentry 路径断了三天才发现。

踩到的五个坑

软链要按目标名重建，不能按源名猜

conda-forge 的 coreutils 装的是原名 cat、ls、date。系统里早就有 BSD 版本，所以 /usr/local/bin 里全是 g 前缀的链接：

1
2

/usr/local/bin/gcat -> ~/opt/main/bin/cat
/usr/local/bin/gls  -> ~/opt/main/bin/ls

我第一版迁移脚本按源文件名反推目标，生成了 ~/opt/main/bin/gcat——文件不存在，101 个 g* 链接全断。修的时候必须按目标 basename 匹配，源文件名在这里是个陷阱。

目录树脚本不能直接软链

yarn 在 Darwin 上的启动脚本这么定位自己：

1
2
3

argv0=$(echo "$0" | sed -e 's,\\,/,g')
case "$(uname -s)" in
  Darwin) basedir="$(cd "$(dirname "$argv0")" && pwd)";;

它用 $0 找同目录的 yarn.js。把 /usr/local/bin/yarn 软链到 conda 的脚本，$0 还是 /usr/local/bin/yarn，于是去找 /usr/local/bin/yarn.js：

1

Error: Cannot find module '/usr/local/bin/yarn.js'

正确做法是写 exec 包装，让 $0 变成真实路径：

1
2

#!/bin/sh
exec /Users/polus/opt/main/bin/yarn "$@"

凡是「脚本 + 同目录资源」的组合都别软链，npm、部分 Python 入口脚本同理。

依赖 CONDA_PREFIX 的启动器

jdtls 的启动器只有一行：

1

exec ${CONDA_PREFIX}/libexec/jdtls/bin/jdtls "$@"

不激活环境时 CONDA_PREFIX 是空的，直接报错。包装脚本里写死：

1
2
3
4
5

#!/bin/sh
CONDA_PREFIX=/Users/polus/opt/main
JAVA_HOME=/Users/polus/opt/main/lib/jvm
export CONDA_PREFIX JAVA_HOME
exec "$CONDA_PREFIX/libexec/jdtls/bin/jdtls" "$@"

JAVA_HOME 也要固定。不固定的话会捡到 sdkman 的 JDK 25，JDT 不一定认；conda 前缀里自带的是 25.0.2 的 Zulu，跟 jdtls 一起测过。

外部程序里写死的绝对路径

迁移完之后 gpg --list-secret-keys 一切正常，但签名时 gpg-agent 会去旧前缀找 pinentry：

1
2

~/.gnupg/gpg-agent.conf:
pinentry-program /Users/polus/opt/cli2/bin/pinentry

改完配置还要重启 agent，否则不生效：

1

gpgconf --kill gpg-agent

这类「配置里写绝对路径」的地方最容易漏：gpg-agent、launchd plist、编辑器 LSP 配置、shell rc。准备删旧前缀之前，最后一步永远是全局 grep：

1
2

grep -rl "opt/cli2\|opt/gitonly\|opt/clitools" \
  ~/.zshrc ~/.config ~/Library/LaunchAgents 2>/dev/null

断链不会报错

软链指向不存在的文件时，系统不会提醒你，只有真正用到的那天才会炸。所以迁移的最后一定要全量扫一遍：

1
2
3
4

import pathlib, os
bad = [(p.name, os.readlink(p)) for p in pathlib.Path("/usr/local/bin").iterdir()
       if p.is_symlink() and not p.exists()]
print(bad)

再接一个 --version 批量自检，跳过 htop、vim 这类交互式的。最后 158 条软链里 155 个有版本输出，剩下 3 个是 git credential helper、gtest 和 mvnDebug，本来就不打印版本。

接进原来的自动更新

我本来有个 brew-daily-update.py，每周三凌晨跑 brew 和一堆上游二进制。加了个 --with-conda，把 conda 也纳进来：

  • CONDA_PREFIXES = ("main", "gnupg")，只处理存在 conda-meta 的目录
  • 每个前缀跑 micromamba update -y -p <prefix> --all
  • 更新前后各取一次 micromamba list --json，做版本 diff
  • 失败计入退出码和通知标题，和 brew 失败同级

--json 的返回结构有两种，直接当 list 解会在某些版本上崩：

1
2

data = json.loads(out)
pkgs = data if isinstance(data, list) else data.get("packages", [])

两个前缀一次完整更新大约 83 秒，大头是拉 repodata，实际升级通常几秒。

cask 这一层：conda 替代不了

11 个 cask 里只有两个在 conda-forge 有包：

caskconda-forge
codex0.169.0，和 brew 版本一致
agentsview0.36.1，落后上游 0.47.0 十来个版本
dbeaver / dbx / drawio / libreoffice / maccy / obsidian / tolaria / hiddenbar / puremac没有

结论很清楚：conda 顶不掉 cask，GUI 只能选 brew cask 或者自己下 dmg。

让 brew 忘掉一个 cask，但保留 app

brew uninstall --cask 会把 /Applications 里的 app 一起删掉。只想解除管理的话，brew 判断「已安装」的唯一依据是 /usr/local/Caskroom/<cask> 目录，把它挪走就行：

1

shutil.move("/usr/local/Caskroom/obsidian", backup_dir)

挪完 brew list --cask 里就没了，/Applications/Obsidian.app 原封不动。前提是确认 app 真在 /Applications，别对把二进制整个放在 Caskroom 的 cask 动手——codex 就是那种，449M 全在 Caskroom 里。

拆 cask 之前先看它建的软链

LibreOffice 和 drawio 的软链不指向 app，而是指向 Caskroom 里的 wrapper：

1
2

/usr/local/bin/soffice -> /usr/local/Caskroom/libreoffice/26.8.2/.homebrew-command-wrappers/soffice
/usr/local/bin/drawio  -> /usr/local/Caskroom/drawio/32.6.10/.homebrew-command-wrappers/drawio

里面的内容就是一句 exec /Applications/....app/Contents/MacOS/xxx。Caskroom 挪走后这些链接全断，得手工改成直连：

1

ln -sf /Applications/LibreOffice.app/Contents/MacOS/soffice /usr/local/bin/soffice

codex 换 bun 装

codex 是唯一一个每天都要用、又留在 Caskroom 里的 CLI，换掉最划算：

1

bun install -g @openai/codex

BUN_INSTALL=/usr/local 时全局 bin 就是 /usr/local/bin，装完直接可用，之后跟 bun update -g 一起升级。旧的 cask 软链要先删，否则 bun 会撞上同名文件。

最后的状态

1
2
3
4
5

brew list --formula       0
brew tap                  0
brew list --cask          agentsview hiddenbar puremac
micromamba list -p main   93
micromamba list -p gnupg  24

/usr/local/Caskroom 从 449M 降到 36K，Homebrew 本体 190M 留着当 GUI 安装器。旧前缀删掉之后省了 2.5G，/usr/local/bin 里 158 条软链全部指向新前缀。

什么时候别搬

不一定都要像我这样搬干净。这几种情况留着 brew 更省事：

  • GUI 应用多，brew cask 仍然是最好的安装和升级渠道
  • 有包需要 brew keg 当 :build 依赖（这台机器是 cmake，被 24 个包依赖）
  • 依赖 brew services 管后台服务
  • 只想解决「编译慢」，那就只迁最贵的那批：Rust 写的 CLI、go 工具链、node、git

混用也不冲突，只要 PATH 顺序固定，让 conda 前缀优先。真不建议的是像我最开始那样分六个前缀——装的时候爽，维护的时候全是负担。
