在 Intel Mac 上跑 OvisOCR2：MPS 走不通，Metal 补丁走通了

2019 款 MacBook Pro 16，i9-9880H 加 AMD Radeon Pro 5500M（8GB），不是 Apple Silicon。要跑的是 OvisOCR2，ATH-MaaS 的 0.8B 端到端文档解析模型，喂整页图片直接吐 Markdown，公式 LaTeX，表格 HTML，图带位置坐标。

网上的教程基本都假设有 M 系列芯片。折腾下来：PyTorch 被版本链卡死，llama.cpp 官方 Metal 在独显上直接崩，最后靠 ToshLLM 的一百多个补丁跑通，视觉编码 4.8 秒。往上又做了一层通用文档转换，24 页的论文一分多钟转完。

代码在 ovisocr2-mac，补丁拆成 llamacpp-metal-amd。

结论先放这

方案结果说明
PyTorch + MPS不可行版本链死锁，本机 torch 上限 2.2.2
llama.cpp Metal（官方）输出损坏GPU Timeout，输出退化成 @@@@
llama.cpp Vulkan输出损坏输出全是 1，根因没查到
llama.cpp CPU能用但慢单页视觉编码 159 秒
llama.cpp + ToshLLM 补丁能用视觉编码 4.8 秒，输出正确

PyTorch + MPS 走不通

不是配置问题，是版本链死锁：

1
2
3
4
5

OvisOCR2 基于 Qwen3.5 架构
  └─ transformers 要 >= 5.0          （只有这样才认识 qwen3_5）
       └─ transformers 5.x 写死要求 torch >= 2.5
            └─ 但 PyTorch 从 2.3.0 起不再发布 macOS x86_64 wheel
                 └─ 本机最高版本停在 2.2.2

放宽版本检查立刻撞墙：ImportError: cannot import name 'DTensor' from 'torch.distributed.tensor'。transformers 5.17 里 DTensor 用了 85 次、device_mesh 73 次、flex_attention 53 次，加上 torch.compile 那 156 处，逐个打补丁不现实。

顺带发现这台机器的 MPS 其实是好的：1024×1024 矩阵乘 ×100，MPS 0.435 秒 vs CPU 0.561 秒；DeltaNet 那几个关键算子（cumsum、einsum、triu、手写 RMSNorm）全部算对，相对误差 1e-7。唯一的硬件限制是不支持 bf16，而 OvisOCR2 权重正是 bf16。卡住的是 PyTorch 不再给 Intel Mac 发 wheel，不是硬件。

官方编译的两条图形后端都挂了

Homebrew 从 2026 年 9 月起不再支持 Intel x86_64 macOS，装的 llama.cpp 根本没编译 Metal，--list-devices 只列出 BLAS: Accelerate。下面两条都是自己编译的。

Metal：设备识别没问题，视觉编码从 159 秒降到 39 秒，但输出是坏的：

1
2
3

ggml_metal_synchronize: error: command buffer 0 failed with status 5
error: Caused GPU Timeout Error (00000002:kIOAccelCommandBufferCallbackErrorTimeout)
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@...

根因在 issue #15228：Metal 后端用 newBufferWithBytesNoCopy(... MTLResourceStorageModeShared ...) 把权重映射成共享内存（ggml-metal-device.m:2214）。核显上没事，独显上 GPU 每算一次都要走 PCIe 从系统内存搬权重，带宽卡死触发超时。issue 被关成 not planned，官方不打算修。

Vulkan：设备能识别，输出全是 1。日志里那条 the CLIP graph uses unsupported operators 不是原因——同一个模型在打补丁的 Metal 上跑得完全正确，告警列表一模一样，那句话只是说算子回退 CPU、性能打折。Vulkan 全 1 的根因没查到，症状和 issue #20104 对得上。运行前要 export VK_ICD_FILENAMES=/usr/local/etc/vulkan/icd.d/MoltenVK_icd.json。

ToshLLM 的补丁

ToshLLM 把 llama.cpp 的 Metal 后端改了个遍。做法是拉它 pin 的 commit，119 个补丁按文件名顺序打上去重编。启动日志里这两行是补丁生效的硬判据，官方构建的二进制里连字符串都没有，grep -a 就能验：

1
2

ggml_metal: device 0: AMD Radeon Pro 5500M (peer group 0, not bridged)
            probed SIMD-group width = 32 (32 = Apple/AMD RDNA, 64 = AMD GCN/Vega)

not bridged 说明认出了独显，SIMD-group width = 32 说明按 RDNA 组宽调度。同一条命令、同一张 1240×1754 页面：

后端视觉编码输出
Metal（官方）39.4 s@@@@ + GPU Timeout
Vulkan（官方）~27 s全为 1
CPU159 s正确
ToshLLM Metal4.8 s正确

119 个文件里光 0001 和 0002 就 15788 行，等于重写了整个 Metal 后端，换 commit 不是随手能升的。

补丁里没有一处提到 Ovis，改的全是 llama.cpp 自己的 Metal 后端和 ToshLLM 的动态 MoE，所以拆成独立仓库。OCR 仓库用 submodule 引它，好处是不用在自己仓库里再分发一遍 GPL-3.0（自己保持 MIT），而且 submodule 天然指向确定的 commit。代价是克隆要带 --recurse-submodules，构建脚本发现目录空会自己补拉。

./scripts/verify.sh 自检不用加载模型，就查那行 probed SIMD-group width，几秒出结果。

分辨率有个硬上限

macOS 的 GPU watchdog 掐的。分辨率越高，单次 command buffer 越久，超阈值输出直接损坏：

长边视觉编码结果
16003.1 s正常
20007.6 s正常
240018.2 s出现 timeout，这次侥幸正确
2800+18.4 s输出损坏

绕不过去：sysctl debug.iogpu.* 不存在，nvram boot-args 是空的，-ub 128 调小 batch 没用，增加 command buffer 数量也没用。所以默认 --max-side 1600，超过 2000 压回 2000，同时检测 @@@@ 和重复 ## 1 这两种退化输出并告警。

单页时间花在哪

拿 Tree Borrows 论文第 16 页测，两张表格，190 DPI 渲染：

阶段耗时
视觉编码4.76 s
解码（输出 551 个词）~16 s
进程启动 + 模型加载~2 s
端到端27.9 s

这几项分开测的，不能相加。权重 700MB 被系统缓存之后加载很快，真正拖时间的是解码。

常驻服务

llama-mtmd-cli 跑完就退出，每个进程都要重新 mmap 权重、建 Metal 计算图、初始化 mtmd 上下文。一张 320×320 白图配 -n 2 空转，整个进程 7.6 秒：加载 2.1 秒，视觉编码 3.6 秒。24 页全量就是重付 23 次加载。

llama-server 把这些全留在进程里，请求只付视觉编码和解码，这个 fork 支持 --mmproj，走 /v1/chat/completions 就行。实测（Tree Borrows 那 24 页）：

场景耗时
4 页，每页起一个进程98.6 s
4 页，常驻服务87.9 s
2 页，冷启动36.5 s
2 页，连到已经在跑的服务25.3 s

单页平均省 2.3 秒。默认常驻，--no-server 退回每页起进程。端口 8181 被占用就顺延，已有同模型实例直接复用；-c 也是启动参数，所以复用时校验模型路径、modalities.vision 和 n_ctx，调用方点名 -dev 或 --no-mmproj-offload 时不复用。slot 固定 1。

scripts/build.sh 里补了一步 cmake --build -t llama-server——llamacpp-metal-amd 只编了 mtmd-cli，补丁在 ggml 层对 server 一样生效。补编失败不致命，找不到就退回逐页起进程。

两个坑。

image 块必须排在 text 块前面。 CLI 把媒体标记拼在 prompt 最前面（mtmd_default_marker() + params.prompt），服务端按 content 数组顺序展开，反了 prompt 就真的不一样，页面被拆段、公式被拆成两个 $$ 块。不明显，两条路径都正常返回结果，只是内容有出入。

输出不保证和 CLI 逐字节相同。 prompt 拼装逐块一致（同样 35×50 网格、122 个文本 token），但 decode 调度不同：CLI 把媒体块和文本块合成一次 llama_decode，服务端分两次，浮点累加顺序变了，贪心解码在接近的 logit 上可能翻牌。pdf2md 取用的 <table> 和 <img> bbox 没受影响，论文那几页逐字节相同；自由格式的 Markdown 不一定，测试页上出现过段落被拆开、border="1" 变 border=1。要严格复现加 --no-server。

这里我一开始拿那几页跑出来一致就说成「逐字节相同」，其实只是恰好一致，结论不能拿几页样本推。

整份文档转 Markdown

正文交给 OCR 太慢，交给文本提取又丢表格和图。所以 anydoc（Rust，毫秒级，文本层和字体元数据最全，但把表格压平、图片丢掉）转全文，pymupdf 挑出含图表的页，只对这些页跑 OvisOCR2，最后按文本锚点插回正文。

1
2
3

python src/pdf2md.py paper.pdf -o out/
python src/pdf2md.py paper.pdf -o out/ --pages 6,12     # 手动指定
python src/pdf2md.py scan.pdf  -o out/ --no-anydoc      # 扫描件

挑页的信号

OCR 一页二三十秒，误判一页白扔三四十秒。一开始的规则很粗：

1
2
3

n_img = len(page.get_images(full=True))      # 位图对象
n_tab = len(page.find_tables().tables)       # pymupdf 判定的表格
n_draw = len(page.get_drawings())            # 矢量绘图数量 >= 15

5224 页语料上命中 89.1%，等于没筛。假阳性分别是每页右上角的 logo、代码清单里带框的标签列表被当成 3×2 的表、4×4 的箭头头部和页眉细线都算一条路径。Tree Borrows 第 14 页正好占后两条：pymupdf 把 root: Unique 这几个带框标签看成 3 行 2 列的表，可每行只有一列有内容（填充率 50%），矢量路径又有 30 条刚过 15 那条线，跑完既没表格也没图。

现在改成：

  • 位图：面积至少占页面 0.5%
  • 表格：rows >= 3、cells >= 6，平均每行至少 1.5 个非空格。按「非空格 / 行数」卡而不是按行列数卡，才不会误杀稀疏的真表（有份社保缴费明细 420 个格子、填充率才 53%）
  • 矢量：取墨迹包围盒，占页面 15% 以上、且高度到 150pt；铺满 60% 以上的单个矩形当背景剔掉

矢量用包围盒不累加面积，是因为这两种图形状相反：状态机是几十条散开的小笔画，单条小但整体摊在一大片上，包围盒就很大；代码块的灰底板是几个大矩形，面积一累加就爆表。高度是第二道保险，图是成块的，代码清单是横条。

同语料降到 28.5%，掉的都该掉：

文档旧新
expense-servicek.pdf30333
JuiceFS 产品白皮书.pdf3512
tree-borrows.pdf43
unsound-oopsla16.pdf10

前三类是每页一枚 logo 或代码清单。阈值有开关 --min-image-area / --fig-area / --fig-height，命中理由会打出来：命中原因: p6=figure p12=figure p16=table。

有个漏检：靠填充矢量图形画的图会漏，墨迹不到 15% 的信息图抓不到（OpenHarmony 年报 p31 只占 9.5%、28 个 item），整页是位图的反而没事。遇到了调小 --fig-area。

试过几个走不通的特征，省得再试一遍：路径条数分不开（真图 37/35，假阳性 30）、曲线数量分不开（有页 104 个）、连通分量聚类没用（笔画散开，最大一块占 1%）、文本密度方向是反的（真图 0.45，代码块 0.18）。

两个小坑

插回正文靠锚点定位。归一化把连续空白折叠成一个空格，插入函数一开始只数非空白字符，两边坐标系对不上，位置不断前移，最后插进单词中间，tracking 被切成 t 和 racking。不报错也不抛异常，只会悄悄把文档切坏。修法是插入函数也把空白当占位字符数。

docx/pptx/xlsx 不用 OCR，anydoc 的 to_document() 直接给结构化对象，合并单元格和图片原始字节都在。两个 API 坑：to_document() 不接受 PDF（报 UnsupportedError）；to_markdown() 处理 docx 时图片完全消失，连占位符都不留。测试 docx 走这条路 0.26 秒结束。

复现

1
2

./scripts/build.sh
HF_BASE=https://hf-mirror.com/Abiray/OvisOCR2-GGUF/resolve/main ./scripts/build.sh   # 国内镜像

环境检查 → Python 依赖 → GGUF 权重 → 调 submodule 构建 llama.cpp → 补编 llama-server → 冒烟测试。每步先检查是否已完成，重复执行直接跳过，首次编译 5～15 分钟。

构建脚本踩过一个自己挖的坑：最早 tmp/llama.cpp 是官方构建留下的目录，里面躺着一个没打补丁的 llama-mtmd-cli，脚本只判断「二进制存在就跳过编译」，于是补丁打上了、编译跳过了、自检去查那个没打补丁的二进制，报「没有检测到 Metal 设备」。现在补丁标记会写进构建目录，对不上就把旧目录移开重编。

常用命令：

1
2
3
4

python src/ovisocr2_llama.py page.jpg -o out                 # 单页，默认 1600
python src/ovisocr2_llama.py scans/ -o out --max-side 2000   # 更清晰更慢
python src/ovisocr2_llama.py page.jpg -o out -v              # 透传 llama.cpp 日志
python src/pdf2md.py paper.pdf -o out/ --fig-area 0.08       # 放宽矢量判据

找二进制的顺序是 tmp/llama.cpp/build-metal/bin/llama-mtmd-cli → 全局安装 → PATH → 官方构建。

还没解决的问题

  • 分辨率天花板锁在 2000，小字密的文档（扫描合同、竖排古籍）可能不够用，没找到绕过 watchdog 的办法
  • ToshLLM 补丁绑定特定 commit，跟进上游得重新适配一万多行补丁
  • OvisOCR2-Q8_0.gguf 在镜像上下载不完整，只到 1.9MB，目前只用 Q4_K_M
  • 靠填充矢量图形画的图还会漏，整页位图没问题，纯矢量信息图要靠 --fig-area 往下调
  • 常驻服务和 llama-mtmd-cli 的自由格式输出不保证逐字节相同，原因是 decode 调度不同导致的浮点差异，没找到对齐的办法
