Dada 的内部引用

来源：Dada: internal references，Niko Matsakis，2026-02-27 系列：Dada

Rust 里这段代码编不过，因为 items 从 list 借，而 list 被移走了：

1
2
3
4
5

struct Message {
    list: String,
    items: Vec<&str>, // 想持有 list 里那些字符串的引用
}
let message = Message { list, items }; // 错误

Dada 把这条限制拿掉了：引用类型命名的是借用的位置（place），不是生命周期。items 的类型写成 ref[list] String，于是“从别的字段借”可以直接表达：

1
2
3
4
5
6

class Message(
    list: String
    items: Vec[ref[self.list] String]
)

let message = Message(list.give, items.give)

list 和 items 一起移进去也没问题。之所以 Dada 做得到而 Rust 做不到，根源在两边对“引用”的定义不同。

Dada 的引用不是指针

1
2
3
4

// Rust：p 指向栈上的 ch
let ch = Character { ... };
let p = &ch;
let q = &ch.name;

1
2
3
4

# Dada：p 是 ch 的浅拷贝
let ch = Character(...)
let p = ch
let q = ch.name

差别在于：Dada 里 x: ref String 本身就是一个 String 值，内存布局和 given String、shared String 完全一样，区别只在“是否拥有内容”。所以也没有 *x 这种解引用——变量里装的永远是值。

代价是栈上占的内存更多，但堆上的数据不复制，而数据绝大多数在堆上。

由此改变的三件事

引用是默认的。 let p = ch 不移动 ch，而是创建引用（显式写是 ch.ref，但不推荐）。要移动得用 .give。

移动被借用的数据是合法的。 Rust 禁止这个，理由有两条：引用是指针，移动会让它失效；类型系统会跟丢——借用检查器内部并不真的知道 name 是从 ch 借的。这两条在 Dada 都不成立：引用不是指针，不会被移动搞失效；类型里写的就是真实变量名，可以跟着改。

编译器在类型里跟踪移动，这叫 strong update：

1
2
3
4

let ch: given Character = Character(...)
let name: ref[ch.name] String = ch.name
let ch1 = ch.give
let name1: ref[ch1.name] = name

把 ch 移进 ch1 之后，name 的类型跟着更新，仍然合法。碰上控制流就要合并：如果 if / else 两条路径的移动情况不同，name 的类型会变成 ref[ch.name, ch1.name] String——满足任一处即可，代价是两条路径上 ch 都算被借用。

借用值传参靠重命名

1

fn character_and_name(ch1: given Character, name1: ref[ch1] String) { ... }

类型检查器把调用脱糖成临时变量，临时变量的类型取自函数签名，但里面的 self 会重写成指向新的临时变量：

1
2
3
4

character_and_name(ch.give, name)
# 展开为
let tmp1: given Character = ch.give
let tmp2: ref[tmp1.name] String = name

传错地方（比如传 ch1.name）类型就对不上，直接报错。类构造函数在类型系统看来就是一次普通调用，只是签名里的 self 要特殊处理。

和 Rust 对照

RustDada
引用是什么指针值的浅拷贝
类型里写什么生命周期，也就是代码区间借用的位置，ref[list]
移动被借用的数据禁止允许，类型跟着更新
*x有没有
str / String两个类型一个类型

能不能搬到 Rust

大部分可以，但有个改不动的硬约束：&T 在 Rust 里就是指针。不过这没听起来那么致命——想引用的数据通常在堆上，移动原值并不会让指针失效：

1
2
3
4

struct Message {
    list: String,
    items: Vec<&{self.list} str>,
}

这里 str 的数据在堆上，移动字符串不会让 &str 失效（但会让 &String 失效）。今天的编译器不知道这些细节，因为 String 有 Deref 实现，str 是否堆分配对它不透明。推进这块的工作在 Beyond the & 目标和 Field Projections 里。
