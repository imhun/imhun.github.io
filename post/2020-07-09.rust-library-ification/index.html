library-ification

来源：Library-ification，Niko Matsakis，2020-04-09

把 rustc 重构成一组独立库、用 query 系统串起来。这个方向有两层收益。

第一层：分析工具拿得到数据

Prusti、MIRAI、Clippy 这类工具想在类型系统之上叠加额外的分析。理论上 Rust 特别适合做这个：C#/Java 那种到处共享可变别名让分析极难，而 Rust 的借用检查天然把“这个函数可能读改哪些数据”变得清楚——分析工具需要的别名分析，和编译器已经在做的事情对应得很好。

实践上却很难，问题不在语言：需要的信息拿不到。Prusti 只能去读借用检查器的 debug 输出再拼出发生了什么。

想要的是这样一条路：分析工具用编译器解析代码、跑借用检查、构造 MIR，然后拿到 MIR 和借用检查结果来搭自己的内部 IR（几乎所有这些验证器都更愿意从 MIR 这个层次出发，而不是原始 AST），顺便还能问内存布局、类型签名。

两个架构趋势正好对上这件事：

趋势内容
on-demand analysis把编译器核心组织成一系列 query，每个 query 是纯函数（“解析这个文件”、“类型检查这个函数”）。执行从想要的终态往回推，天然适配增量计算、并行，以及 IDE 那种“只做必要的工作量”。rust-analyzer 完全建立在它上面（用 salsa）
library-ification把编译器切成一组独立库，用 query 串起来

对分析工具来说，on-demand 的价值在于“只索取需要的结果”，而且如果做对了，还能复用编译器正在用的增量缓存——上次构建算过的东西不用重算，甚至下一次构建能复用 Prusti 算出来的结果。

第二层：rustc 和 rust-analyzer 合流

直接动因是想把两者整合进一个代码库。今天 rust-analyzer 基本是把前端重写了一遍：自己的解析器、名字解析、类型检查器。

有意思的是它没有什么——没有自己的 trait 系统，用的是 chalk。把 chalk 集成进 rustc 的工作也在推进。如果成，就能把 “trait solver” 做成一块被多个项目共享的功能，再往前一步：rustc 和 rust-analyzer 只是同一批核心包之上的两个薄壳，一个以批编译形式给 cargo 用，一个作为 LSP server 给 IDE 用。

chalk 的 API 设计还有个关键特征：它建立在核心概念上，通过 RustIrDatabase 这样的 trait 通信，不需要完整 AST 或一堆宿主细节。带来的好处是可以用简化版 Rust 语法写单元测试。

这件事的意义比“可读”更深：作者多次遇到单元测试和代码结构绑死、一重构就废掉一大片的情况，而 rustc 和 chalk 的测试就是示例程序，没这个问题。所以——能不能清楚地写单元测试，是判断库边界划得好不好的一个信号。

判断标准：接口别老变

如果组件之间的接口总在变，说明这些模块的耦合超出了想要的程​​度，也让人更难只待在一个库里面。反过来说，作者喜欢改 chalk 就是因为它窄、好摆弄，跳来跳去很容易找到东西，而改 rustc 感觉困难得多——尽管他对那个代码库相当熟。

对新人来说差别更大：rustc 代码量很大、构建要等、需要自定义设置、吃内存，模块边界又不够明显，很难一块块学。换成少量定义良好的库之后，可以跳进单个库开始干活，它有清晰的 API 连到其余部分，还有测试框架能跑针对这个 API 的单元测试。

终点：这些库也发布出去

如果真切分出连贯的库、API 又相对稳定，就可以把它们（或包一层简化的版本）发布到 crates.io，有点像 .NET 的 Roslyn。那时 Prusti 可以直接调用 rustc 的借用检查器读结果，不用再搞那些费劲的 hack。

关于“稳定”

作者明确否掉了给 rustc 或它的库承诺固定不变 API 的想法。早期就是每个 Rust 版本给每个库发一个新的 major 版本，意味着你得经常更新。等 API 稳定下来（他很希望如此），就按普通库的规矩遵守有意义的 semver：随时可以做破坏性改动，但要公告。
