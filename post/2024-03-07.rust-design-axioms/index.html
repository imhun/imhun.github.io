Rust 设计公理

2024-03-07
技术
1007 words 3 mins read times read

Contents

    • 定下来的四条
    • 还在打磨的三条

来源：Rust design axioms，Niko Matsakis，2023-12-07

思路很朴素：做决定的时候，脑子里其实在快速跑一堆假设和直觉，快到几乎注意不到（“可以做 X，但那样就意味着 Y，不想要 Y，算了”）。把这些假设抓出来写清楚，以后做决定就能回头查，团队之间也更容易对齐。在证明系统里公理就是“断言为真、凭信任接受”的东西，这里借的就是这个意思：哪些起始假设一路推下去会把你带到 Rust？

每条公理写成“假设 + 推论”：先说不变量，再说因此我们怎么做。

定下来的四条

按优先级排序，靠前的压过靠后的：

#公理推论
1Rust 的使命是赋权所有人构建可靠、高效的软件所以要易用：不采用复杂到实际用不起来的设计，做支持性工具帮人理解并修好错误
2用户希望问题越早暴露越好所以要可靠：选择能让 bug 更早暴露的做法；不猜用户想干什么；safe code 里永远保证内存安全和免于数据竞争
3用户和我们一样在意质量所以要可扩展：赋权用户自己搭抽象，而不是试图（并且失败于）替他们准备一切
4系统程序员需要知道发生了什么、在哪里发生所以要透明且可调：抽象要让人仍然觉得在掌控底层系统，比如让某类操作容易被察觉或避开

为什么可靠排第二而不是第一？如果可靠性最关键，就不会允许 unsafe——至少不会允许没有安全证明的 unsafe。Rust 的做法是务实的：安全类型系统覆盖 90%–95% 的需求，剩下退回 unsafe。这当然不如 100% 正确性证明可靠，但那种系统由极少数人维护，而“系统编程只有他们才玩得转”恰恰是要摆脱的想法。

还在打磨的三条

不是觉得它们不对，而是不确定措辞和位置：

公理推论
用户想专注解决问题，而不是琐碎细节所以要高效：最方便、最高层的选项同时也是最高效的那个；默认支持跨平台；显式不是为了显式本身，而是把必要的细节摆出来
N✕M 大于 N+M所以要可组合、正交：找那些各解决独立问题又能互相搭建的特性
一门语言好过两门所以要通用：不可能样样最好，但让它对几乎任何事都够用，从底层 C 代码到高层脚本

作者自己对这几条也开了 issue 追问：是不是该单独有一条“性能”公理（现在“零开销抽象”这个想法被分摊在“透明可调”和“高效”里了）；“可移植性”重要到该单独成条吗；“通用性”和“正交性”表达的东西真的和“高效”不一样吗。

背景

作者喜欢 Amazon 的 tenets 那种做法，也承认很多人觉得那是企业废话。但他在 Rust 上看到的一贯主题是流程和结构不可少——团队、RFC、公开的 rfcbot 决策机制，都是把某种不成文的做法定下来。
