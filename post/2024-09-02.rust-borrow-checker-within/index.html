借用检查器内部

来源：The borrow checker within，Niko Matsakis，2024-06-02

借用检查器建立在一条规则上：修改与共享互斥（mutation xor sharing）——用 x 改一个值的时候，不能再通过 y 读它。这条规则撑起了内存安全，也是“能编过就是对的”那种手感的来源。

它既不必要（Java 那种到处共享的程序也能跑），也不充分（所以才需要 Arc<Mutex<T>>、AtomicU32、unsafe）。但学会之后会发现它经常“刚刚好”，而且按这个风格写的程序更不容易让人意外，也就更好维护。

麻烦在于有一批代码符合这条规则，却被借用检查器拒掉。这篇文章给出四步来缩小这个差距。

目前的空白为什么解法进度
条件返回引用NLL 覆盖不了Polonius只剩工程
生命周期没有语法它代表“代码的某个区间”，反直觉且不可见用 place 代替生命周期：'x、'x.y、'(x.y, z)只剩命名之争
辅助方法必须内联借用检查器一次只看一个函数view type：&mut {counter} self需要建模
值和指向自己内部的引用无法打包类型里没有“部分借用”这种状态内部引用已为简化版 Rust 建模

fn get_default<'r, K: Hash + Eq + Copy, V: Default>(
    map: &'r mut HashMap<K, V>,
    key: K,
) -> &'r mut V {
    match map.get_mut(&key) {
        Some(value) => value,
        None => {
            map.insert(key, V::default());
            map.get_mut(&key).unwrap() // 今天报错
        }
    }
}

让生命周期有语法

1
2
3
4

fn get_default<K: Hash + Eq + Copy, V: Default>(
    map: &mut HashMap<K, V>,
    key: K,
) -> &'map mut V { ... }

好处不只是少写几个参数，更是好教。生命周期现在的尴尬在于：它代表的概念用户平时不会去想，而且它没有任何语法形式。有了语法才能把默认藏着的东西写出来；而先把话说全、用熟了再省略，是真正内化一个概念的必经一步——boats 把这个过程叫 dialectical ratchet。

struct WidgetFactory { counter: usize, widgets: Vec<Widget> }

impl WidgetFactory {
    fn increment_counter(&mut self) { self.counter += 1; }

    pub fn count_widgets(&mut self) {
        for widget in &self.widgets {
            if widget.should_be_counted() {
                self.increment_counter(); // 报错
            }
        }
    }
}

借用检查器不知道 increment_counter 只动 counter，只能保守地认为 widgets 可能被改。现在的绕法——把字段引用拆成自由函数，或者搞一个 view struct——都别扭且不局部。有了 view type 就能直接声明：

1

fn increment_counter(&mut {counter} self)

同一套机制还能解决分阶段初始化：先建一部分字段，再调辅助函数建剩下的。

实践中要 view type 的场合大多在私有函数里——私有方法做小块逻辑、用得上内部结构；公开方法倾向于做大事、把内部结构藏起来。而且公开函数保持 &mut self 有前向兼容的好处：改内部用到的字段不影响调用方。

内部引用

struct Message {
    text: String,
    headers: Vec<(&'self.text str, &'self.text str)>,
    body: &'self.text str,
}

Message 不需要生命周期参数，因为它不从自己以外的地方借东西，所以 Message: 'static 成立，可以直接送进另一个线程。

搬到 Rust 上要处理一个额外约束：&T 在 Rust 里真的是指针，这一点改不动。但很多自引用场景没那么在意——想引用的数据通常在堆上，原值移动时指针并没有失效。Rust 这边相关的工作在 Beyond the & 目标和 Field Projections 里。

判断标准：错误能不能就地处理

1
2

error[E0502]: cannot borrow `*self` as mutable
              because it is also borrowed as immutable

这个错误没办法用直觉解释，因为概念上它本来就该能编过，只是撞上了类型系统的限制。想知道为什么编不过，只能深挖类型系统的工程细节——而这正是人们不想学的东西。更糟的是，深挖完之后能得到的最好结果也就是一个别扭的绕法。

有了 view type，同一条错误会多出一条建议：

1

help: annotate with accessed fields: `&mut {counter} self`

照做就能接着干活，想深挖可以之后再挖，而且那时你知道该学什么、为什么学。这就是判断标准：改动是让错误变得可处理，还是要求用户先学会编译器内部。

共同主线

四步做的是同一件事：把借用检查器的分析从“编译器脑子里的状态”搬进能写出来的类型里。现在所有类型都表示完全初始化、未被借用的值，没法表达“正在迭代中”或者“移动了一两个字段但没移动全部”。

至于优先级——作者说他一度觉得花时间搞借用检查器的人体工学有点愧疚，把 RustNL 上的对话当成转折点：人们抱怨的痛点集中在做应用和 GUI 的人身上，而他意识到自己中了“知识的诅咒”，忘了撞上限制又不知道绕法有多让人烦躁。
